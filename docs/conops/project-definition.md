## 2. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | FridgeMate: OSS 기반 냉장고 식재료·유통기한 관리 서비스 |
| 형태 | 모바일·PC 브라우저에서 사용하는 웹 앱(PWA) |
| 핵심 개념 | 식재료를 쉽게 등록하고, 유통기한이 다가오면 알려 주며, 남은 재료로 만들 수 있는 요리를 추천 |
| 수행 방식 | Agile(Scrum), GitHub 기반 협업 |
| 수행 기간 | 5주 (Sprint 1~5) |
| 팀 구성 | 이정남(팀장), 이석환(개발자), 이지선(Reviewer) |

**프로젝트 정의:** 가정에서 식재료가 잊혀 버려지는 문제를 줄이기 위해, 공개된 오픈소스 소프트웨어(OSS)를 조사·평가·선정하여 식재료 관리 서비스의 구조를 설계한다.

## 3. 프로젝트 배경

- 1인 가구와 맞벌이 가구가 늘면서 장보기는 몰아서 하고, 냉장고 관리는 소홀해지는 경우가 많다.
- 냉장고 안쪽이나 냉동실에 넣어 둔 식재료는 존재 자체를 잊기 쉽고, 결국 유통기한이 지나 버려진다.
- 같은 재료를 이미 갖고 있는데도 또 사는 중복 구매가 발생한다.
- 바코드 인식, 문자 인식(OCR), 공개 식품 데이터베이스 등 관련 기술이 OSS로 공개되어 있어, 직접 개발하지 않고도 빠르게 서비스를 구성할 수 있는 환경이 갖춰져 있다.

## 4. 현재 문제점 (AS-IS)

| ID | 현행 문제 | 원인 | 영향 |
|---|---|---|---|
| PB-01 | 보유 식재료 파악 어려움 | 냉장고를 직접 열어 봐야만 확인 가능 | 장보기 계획 수립 어려움 |
| PB-02 | 유통기한 관리 부재 | 기억이나 메모에 의존 | 기한을 놓쳐 식재료 폐기 |
| PB-03 | 음식물 폐기 증가 | PB-01, PB-02의 누적 | 식비 손실과 환경 부담 |
| PB-04 | 중복 구매 | 장보는 시점에 보유 재료를 모름 | 불필요한 지출, 보관 공간 부족 |
| PB-05 | 등록의 번거로움 | 기존 앱은 품목을 하나씩 손으로 입력 | 사용 중단, 데이터 부정확 |
| PB-06 | 가족 간 정보 공유 어려움 | 냉장고 정보가 개인 머릿속에만 있음 | 중복 구매, 소비 시점 엇갈림 |

## 5. 프로젝트 필요성

- **생활 측면:** 식재료를 기한 안에 소비하도록 도와 식비와 음식물 쓰레기를 줄인다.
- **기술 측면:** 바코드 인식, OCR, 상품 정보 DB, 푸시 알림 등 검증된 OSS를 조합하면 짧은 기간에 실용적인 서비스를 만들 수 있다.
- **교육 측면:** 요구사항 정의부터 OSS 검색·평가·선정, 통합 설계까지 OSS 활용 개발의 전체 과정을 실습할 수 있다.

## 6. 목표 시스템 개념 (TO-BE)

```
[등록]            [보관 관리]            [알림]              [활용]
바코드 스캔  →   보관 위치별 목록   →   유통기한 임박 알림  →  남은 재료로 레시피 추천
직접 입력        (냉장/냉동/실온)       (D-3, D-1, 당일)       소비/폐기 기록
                       ↑                                             │
                       └──────────── 가족 구성원과 공유 ←─────────────┘
```

## 7. 프로젝트 목표

### 7.1 정성 목표
- 식재료 등록을 쉽고 빠르게 만들어 꾸준히 사용할 수 있게 한다.
- 유통기한이 지나기 전에 사용자가 인지하고 소비하도록 돕는다.
- 각 기능에 적합한 OSS를 근거 있게 선정하고 통합 방안을 제시한다.

### 7.2 정량 목표

| 목표 ID | 목표 | 성공지표 |
|---|---|---|
| OBJ-01 | 식재료 1건 등록 시간 | 바코드 사용 시 10초 이내 |
| OBJ-02 | 바코드 인식 성공률 | 일반 가공식품 기준 90% 이상 |
| OBJ-03 | 유통기한 알림 | 설정한 시점(D-3, D-1, 당일)에 누락 없이 발송 |
| OBJ-04 | 화면 응답 시간 | 목록 조회 2초 이내 |
| OBJ-05 | OSS 평가 | 기능 영역별 후보 3개 이상 비교 후 1개 선정 |

## 8. 시스템 범위

### 8.1 포함 범위

| 구분 | 내용 |
|---|---|
| 회원·공유 | 회원가입·로그인, 가족(냉장고) 단위 공유 |
| 식재료 등록 | 바코드 스캔으로 상품 정보 자동 입력, 직접 입력 |
| 식재료 관리 | 보관 위치(냉장/냉동/실온)별 목록, 수량·유통기한 수정, 소비/폐기 처리 |
| 알림 | 유통기한 임박 푸시 알림 |
| 레시피 추천 | 보유 식재료와 임박 재료 기반 레시피 추천 |
| OSS 활용 | 각 기능에 적용할 OSS 검색·평가·선정 및 통합 설계 |

### 8.2 제외 범위

| 구분 | 제외 사유 |
|---|---|
| 스마트 냉장고 기기 연동(IoT 센서, 카메라) | 하드웨어 필요, 실습 기간 초과 |
| 온라인 장보기·결제 연동 | 외부 상용 서비스 계약 필요 |
| 영수증 OCR 자동 등록 | 인식 정확도 문제로 확장 기능으로 분류 (후속 과제) |
| 영양 성분 분석·식단 관리 | 핵심 문제(폐기 감소)와 거리가 멀어 제외 |
| 앱스토어 네이티브 앱 출시 | PWA로 대체 |

### 8.3 시스템 경계

| 구분 | 시스템 내부 | 시스템 외부 |
|---|---|---|
| 데이터 | 식재료 정보 저장·조회·수정, 유통기한 계산 | 상품 정보 원천 데이터(공개 상품 DB) |
| 등록 | 바코드 인식, 직접 입력 화면 | 스마트폰 카메라 하드웨어 |
| 알림 | 알림 대상 판별, 발송 요청 | 브라우저·OS의 푸시 알림 전달 |
| 사용자 | 회원 인증, 냉장고 그룹 공유 권한 | 외부 소셜 계정 서비스 |
| 추천 | 보유 재료와 레시피 매칭 | 레시피 원천 데이터(공개 레시피 데이터) |

## 9. 이해관계자

| 이해관계자 | 역할 | 기대가치 |
|---|---|---|
| 1인 가구 사용자 | 주 사용자 | 식재료 낭비와 식비 절감 |
| 가족 공유 사용자 | 공동 사용자 | 구성원 간 냉장고 정보 공유, 중복 구매 방지 |
| 교수자 (Product Owner) | 과제 범위 승인, 결과 검토 | 체계적인 OSS 활용 개발 과정 수행 |
| 개발팀 | 설계·문서 작성·OSS 평가 | Agile 협업과 OSS 평가 역량 습득 |
| OSS 커뮤니티 | 사용 OSS 제공 | 라이선스 준수, 이슈·개선 피드백 |
| 공개 데이터 제공자 (예: Open Food Facts) | 상품 정보 제공 | 데이터 출처 표시와 이용 조건 준수 |

## 10. 예상 효과

- 유통기한 경과로 버려지는 식재료 감소
- 중복 구매 감소로 식비 절감
- 가족 간 냉장고 정보 공유로 장보기 효율 향상
- OSS 조합으로 개발 기간과 비용 절감, 재사용 가능한 OSS 평가 기준 확보

## 11. 가정사항 및 제약사항

### 11.1 가정사항
- 사용자는 카메라가 있는 스마트폰 또는 PC 브라우저를 사용한다.
- 가공식품은 공개 상품 DB에서 바코드로 상품명을 조회할 수 있다.
- 신선식품(채소, 육류 등)은 사용자가 직접 입력한다.

### 11.2 제약사항
- 수행 기간은 5주이며, 팀원 3명이 수업 외 시간에 작업한다.
- 무료로 사용할 수 있는 OSS와 공개 데이터만 사용한다.
- 사용 OSS는 라이선스 조건을 확인하고 준수해야 한다.
- 사용자 개인정보(계정, 보유 식재료 기록)는 최소한으로 수집한다.
- 모든 산출물은 GitHub 저장소에 Markdown으로 관리한다.

## 12. 초기 위험과 대응방향

| 위험 | 영향 | 대응방향 |
|---|---|---|
| 국내 상품 바코드가 공개 DB에 없음 | 자동 입력 실패 | 직접 입력 기능 병행, 국내 공공 데이터 추가 검토 |
| OSS 라이선스 조건 미확인 | 배포 제약 | 평가 기준에 라이선스 항목 필수 포함 |
| 일정 지연 | 산출물 누락 | Sprint별 범위 조정, MVP 기능 우선 |

## 13. 프로젝트 성공 기준

- 포함 범위의 핵심 기능(등록·관리·알림)에 대해 OSS가 선정되고 통합 구조가 설계되어 있다.
- 정량 목표(OBJ-01~05)를 검증할 방법이 정의되어 있다.
- 모든 산출물이 Issue와 PR로 관리되고, 팀원 Review를 거쳐 main에 Merge되어 있다.
